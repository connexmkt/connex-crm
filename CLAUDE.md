# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev                     # dev server (Next.js)
pnpm build                   # prisma generate + next build
pnpm lint                    # eslint .
pnpm typecheck               # tsc --noEmit
pnpm test                    # vitest run (single run, all suites)
pnpm test:watch              # vitest watch mode
pnpm db:generate             # prisma generate -> lib/generated/prisma
pnpm db:migrate              # prisma migrate dev (local dev migration)
pnpm prisma migrate deploy   # apply pending Prisma migrations (prod/CI)
```

Run a single test file: `pnpm vitest run tests/unit/require-auth.test.ts`
Run tests matching a name: `pnpm vitest run -t "nome do teste"`

CI (`.github/workflows/ci.yml`) runs lint (non-blocking), typecheck, test, and build on every push, then auto-tags/releases `main` via conventional commits (`.github/scripts/bump-version.mjs`) — don't hand-edit `package.json` version or `CHANGELOG.md`, they're generated by that job.

## Architecture

This is a Next.js 16 App Router CRM (`connex-crm`) with a **mandatory layered architecture** enforced by `.specify/memory/constitution.md` (the highest-authority doc in this repo — read it for the full rationale behind rules below):

```
UI (Server/Client Components) → Services (lib/services/) → Repositories (lib/repositories/) → Supabase
```

- Components **never** call Supabase directly. Route Handlers (`app/api/**/route.ts`) parse+validate the request (Zod), delegate all logic to a `lib/services/*.service.ts`, and only that service talks to a `lib/repositories/*.repository.ts`. No SQL/Supabase calls inside route handlers or components.
- Services take `SupabaseClient` as an explicit first argument (see `lib/services/clientes.service.ts` / `lib/repositories/clientes.repository.ts`) rather than instantiating their own client — this is what makes them unit-testable with mocked clients.
- Route Handlers return responses via the shared helpers in `lib/api/response.ts` (`ok`, `created`, `noContent`, `badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `serverError`, `badGateway`) — use these instead of building `NextResponse.json` ad hoc.
- Every module under `app/` (e.g. `app/clientes/`, `app/pipeline-comercial/`) co-locates its own `components/`, `hooks/`, `schemas/`, `constants/` next to `page.tsx`. Shared UI lives in `components/ui/` (shadcn/Radix primitives) and `components/layout/`.

### Database & auth

- **Supabase Postgres** for the CRM itself (`connex-crm` project). Auth is Supabase Auth via `@supabase/ssr`. `lib/server.ts` creates the request-scoped, cookie-bound client for normal user-authenticated reads/writes (RLS-enforced).
- **Prisma** is currently configured but has no models — all data access goes through the Supabase JS client directly. Do not add new Prisma models for CRM domain data without checking the constitution's data-access rules first. Generated client lives at `lib/generated/prisma` (gitignored, regenerated via `postinstall`/`db:generate`).
- `middleware.ts` / `lib/middleware.ts` (`updateSession`) only handles auth session refresh + redirect-to-login; no business logic belongs there.

### Validation, types, response shape

- All external input (route bodies, query params) is validated with Zod before touching a service. Route-local schemas live next to the route/module; schemas shared client+server live in `lib/schemas/`.
- API success responses are always `{ data, meta? }`; validation errors are `400` with Zod's `.flatten()` under `details`. See `README.md` for the full endpoint reference (auth, clientes, pipeline, conteúdo, atividades, dashboard/relatórios) — treat it as the source of truth for request/response shapes instead of re-deriving them from routes.
- Strict TypeScript throughout: no unjustified `any`; exhaustive `switch` (`default: never`) on domain enums; explicit return types on exported functions in `lib/` and `app/api/`.
- Magic values/enums belong in `lib/constants/`, not inline.

### Spec-driven feature workflow

Features are planned under `specs/NNN-slug/` (spec.md, plan.md, research.md, data-model.md, tasks.md) using the Speckit workflow (`.specify/templates/`, `speckit-*` commands). `.cursor/rules/specify-rules.mdc` points at the currently active spec — check it for in-flight feature context before making structural changes in the area it covers.

### Testing

Vitest + jsdom (`vitest.config.ts`), tests under `tests/unit/` and `tests/integration/`, plus co-located `*.test.tsx` under `components/`. Services/repositories are unit-tested with a mocked `SupabaseClient`; Route Handlers get integration tests covering the happy path plus error paths (401/400/404/409/502 as applicable).
